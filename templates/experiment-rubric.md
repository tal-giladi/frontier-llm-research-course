# Experiment rubric

Use this to assess every module project and the capstone — your own, or a peer's. Each criterion
scores 0 (missing), 1 (partly), 2 (done). A project passes at 10 of 14 with no zero.

**Whether the new method wins is not a criterion.** A sound experiment with a null or negative result
scores the same as one with a positive result.

| # | Criterion | 2 = done looks like |
|---|---|---|
| 1 | Question and decision | One answerable question; the decision it informs is stated before the runs. |
| 2 | Controls | One changed variable (or a declared factorial design); data, eval, seeds and software held fixed and shown to be fixed in the run cards. |
| 3 | Comparison axis and budget parity | The axis is named and justified; budgets match on that axis, including teacher/judge/verifier/generator compute where used; the baseline got the same tuning budget. |
| 4 | Correctness | Every required correctness check passed and its output is included. |
| 5 | Uncertainty | Seed noise floor and/or paired intervals reported; the conclusion respects them. |
| 6 | Conclusion matches evidence | The claim is no stronger than the evidence; analysis of provided traces is labelled as analysis. |
| 7 | Limits | Scale, data and architecture limits stated, with what result would change the answer. |

## Written defence

Each project ends with a 1–2 page written defence answering the reviewer questions in the project
brief. Typical questions:

- Why this comparison axis and not another?
- How do you know the baseline was tuned as hard as the new method?
- What is the smallest effect your design could detect?
- What would you run next with 10× the budget, and what result would make you abandon the idea?
